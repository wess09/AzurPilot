# 异常恢复：原有机制、修复边界与行为对照

## 为什么保留原有持续恢复

AzurPilot 面向长期运行：ADB 抖动可以先重连，游戏卡住可以重启客户端，模拟器确实离线时才需要启动模拟器。模拟器冷启动有时比一次等待更慢，平台层已用启停互斥锁保护正在进行的操作，后续轮次会逐步放宽等待。因此，不能把一次启动未完成当成永久故障，也不能随意加一个总次数上限。

本次先用提交 `67c6b788b` 完整撤回此前的 `d2f2883e1`，恢复到 `8f1858298` 的文件内容，再在旧实现上修复授权边界。此前改动有两个明确错误：MuMu、雷电的原生辅助对象没有收到配置，重试检查反而抛出 `AttributeError`；把 `Reboot.Tries` 用作外层恢复预算，导致默认阈值尚未满足、或模拟器仅尝试一次就退出。新实现不保留这两个行为。

模拟器平台层原有的停止、等待退出、启动、等待 ADB 上线、包名验证、互斥锁和超时预算均保留；没有改动模拟器命令或缩短启动等待。MuMu 深度重启仍受原有独立配置控制。

## 之前与现在

| 情况 | 旧版实际行为 | 本次修复后 |
| --- | --- | --- |
| 关闭异常处理后出现故障 | 多个异常分支仍重连、重启模拟器或安排 Restart；游戏启停函数又一律拒绝，造成上下层不一致 | 检测到需要恢复的错误即保存现场并退出当前自动化 worker；不再恢复、延期或重新调度故障任务 |
| 游戏连续卡死 | 卡死分支检查自己的开关，但游戏启动超时、全局兜底等可能绕过它 | 游戏卡死、启动操作超时、启动观察失败按卡死来源处理；只有总开关、敏感保护、卡死重启开关和次数阈值均允许才升级模拟器 |
| 模拟器或 ADB 持续离线 | 模拟器重启明确忽略离线重启开关；次数阈值只改变退避 | 先检查离线开关；连续检测达到配置次数才请求启停，达到后仍保留持续恢复和原有退避 |
| 未知脚本异常或任务返回失败 | 可能使用卡死计数或失败计数强制重启模拟器 | 保留原有客户端恢复和任务上限，不仅凭未知异常或失败返回值断言模拟器坏了 |
| `ScriptError` | 连续 3 次后退出 | 保留；不会第一次就因脚本错误直接退出，关闭总开关或敏感保护命中时除外 |
| `RequestHumanTakeover` | 统一尝试模拟器和游戏恢复 | 保留任务上限内的客户端兜底，不直接重启模拟器；原有 SP 等局部处理在允许恢复时保留 |
| 运行中关闭监护总开关 | 已存在的线程仍可能只看子开关而执行恢复 | 每轮同时检查监护总开关、子开关和有效超时；执行前再次检查 |
| 启动后才开启监护或日报 | 没有线程，或日报线程退出后不重建 | 设置观察线程读取最新文件；日报按原有实现按需创建、关闭、重建，不重绑正在运行的任务配置 |
| 任务恢复上限改为 0 | 旧的内存冷却和次日排期仍挡住立即运行 | 解除本进程拥有且未被用户改动的故障冷却；用户另设排期、禁用状态保留 |
| 未知页面本地恢复 | 重启游戏后递归识别，持续未知可绕过调度器的业务任务上限 | 保留一次本地客户端恢复；仍未知则上抛，交回原调度器计数，不在 UI 内无限递归 |
| 手动启停、正常主动任务、长等待预热 | 下层总开关可能误拦主动游戏启停；手动模拟器重启先初始化离线设备 | 正常主动操作保留；手动模拟器管理直接使用不连接 ADB 的平台对象；失败后继续恢复才检查总开关 |
| 独立定时重启 | 与其他恢复共用模拟器入口 | 仍按模拟器管理自己的开关和间隔执行；强制计划中断有独立来源，不被误记为普通故障或业务成功 |

## 哪些情况重启、哪些情况停止

| 前提与故障 | 游戏客户端 | 模拟器 | 当前 ALAS worker |
| --- | --- | --- | --- |
| 总开关关闭，发生需要恢复的错误 | 不自动重启 | 不自动重启 | 退出并保留现场 |
| 总开关开启，严格重启且当前任务敏感 | 不自动重启 | 不自动重启 | 按原保护退出 |
| 游戏已退出、客户端 Bug、未知页面 | 保留原有客户端恢复 | 不仅凭此原因重启 | 按原任务上限继续或延后故障任务 |
| 游戏卡死，卡死重启关闭或次数未到 | 保留原有客户端恢复 | 不因卡死重启 | 继续；监护仅观察，不因子开关关闭而停止 worker |
| 游戏卡死，卡死重启开启且达到次数 | 重启模拟器后由 Restart 登录 | 允许 | 继续恢复 |
| 设备确实离线，离线重启关闭 | 可继续原有连接/客户端恢复尝试 | 不因离线启停 | 继续等待连接；不会因此自动打开离线开关 |
| 设备离线，离线重启开启但次数未到 | 保留原有恢复调度 | 暂不启停 | 累计连续检测次数 |
| 设备离线，离线重启开启且达到次数 | 模拟器上线后由 Restart 登录 | 允许持续恢复 | 不因 `Reboot.Tries` 或业务任务上限终止系统 Restart |
| 未知异常、需要人工介入信号 | 保留旧版任务上限内的客户端兜底 | 不据此直接重启 | 记录错误；严格敏感保护或关闭总开关时停止 |
| `ScriptError` 连续达到 3 次 | 停止继续恢复 | 不直接重启 | 退出，等待修复代码 |
| 独立定时重启或明确手动操作 | 按该主动流程执行 | 由自己的设置/请求决定 | 不套用普通异常恢复次数 |

关闭异常处理只限制错误后的恢复，不取消用户主动授权的正常任务。正常任务中的第一次启动失败后，第二次启动、观察重试等就属于异常恢复，必须重新检查授权。

## 次数与等待不是同一回事

- `Error.AdbOfflineThreshold`、`Error.GameStuckThreshold` 是连续检测/错误的**次数**，不是秒，也不是总重启次数上限；界面五种语言已修正。阈值按至少 1 次执行。
- 例如离线阈值为 3：第 1、2 轮不操作模拟器，第 3 轮开始允许操作；如持续失败，第 4、5……轮仍可恢复。超过阈值的退避仍按旧公式逐步增加，最高 300 秒。
- 每次 `_try_restart_emulator()` 只发起一轮平台启停；Windows 平台每次启动仅尝试一轮，失败交回调度器。**一次调用尝试一轮，不等于整个运行周期只重启一次。**原有平台内部的停止补救次数不变。
- 启动监视继续按实际失败次数使用原有 60/90/120/180/300 秒阶梯；离线检测次数与实际启停失败次数分开，避免阈值为 3 时首次启动就误用更高失败档位或深度清场。
- `Reboot.Tries` 只限制一轮游戏启动尝试，之后保留原来的观察阶段；不限制后续模拟器恢复或系统 Restart 调度。启动和观察的等待时长、默认值均未修改。
- `Error.TaskRestartLimit` 仍限制同一业务任务的恢复轮次，达到后延至服务器下一次零点，其他任务继续；0 关闭此限制。只有故障业务任务自己成功才清掉其计数，其他任务或 Restart 成功不清掉它。
- 系统 Restart 仍豁免业务任务上限，避免游戏和模拟器尚未上线时把唯一恢复入口延至次日。
- 独立 Device 构造保留最多 4 次连接检查、最多 3 次启动的局部预算；阈值大于该预算时明确抛回上层，不伪造连接成功。未达到阈值的检查不算启动失败。主调度器使用 `auto_start_emulator=False`，模拟器恢复由外层持续调度，不会被这个局部预算截断。
- 没有新增全局模拟器重启次数上限。持续离线可能一直尝试，用户可关闭对应开关、总开关或停止实例；这保留旧版长期运行能力，并不是修复后“只重启一次”。

## 动态配置、并发与退出

`module/config/recovery.py` 只读已保存 JSON，不调用 `config.load/bind/save`。下层原生对象也持有同一实例配置，MuMu、雷电工厂在初始化前传入它，避免在故障重试中产生缺失属性的新异常。配置文件损坏或真实配置不可读时禁止自动恢复，不以旧的开启状态继续执行。

恢复操作前、底层重试等待前后、重连完成后、下一轮调度前都会重新检查。普通故障的授权归属保留至原任务成功；仅 Restart 成功不足以允许关闭总开关后重跑故障任务。故障任务已延后且必要的 Restart 完成后则结束该恢复，保留其他健康任务正常运行。设备上的临时恢复标记使本地未知页面、大世界迷雾等原地恢复也响应总开关关闭；退出上下文后还原标记，不写进用户配置。模拟器长时间退避后、停止完成而尚未启动时，再次核对对应来源的开关。已经发出的系统命令不能追溯撤销；不承诺中断第三方库尚未报告的故障。

监护超时必须满足自己的两个开关和分钟阈值；涉及模拟器还必须获准卡死恢复且次数足够。监护成功中断一次后不会每个周期重复关闭模拟器，随后的离线恢复保留卡死来源，不能借离线开关绕过卡死设置。模拟器原有平台互斥锁保留；游戏启停硬超时留下的调用未结束时，不叠加第二个同设备调用。

强制定时重启遵守自己的两个开关、时间间隔和非敏感任务条件；仅它造成的预期连接中断可继续计划重启。未知脚本错误不能借这个标记绕过总开关。计划中断不计业务故障次数，也不伪造业务完成状态。

禁用恢复后，主线程抛出退出码 1 的 `SystemExit`；后台监护无法用线程内 `SystemExit` 结束阻塞主线程，因此保存现场后用 `os._exit(1)` 只结束**所在 worker 进程**。不枚举或结束 WebUI、其他 ALAS worker。错误现场遵循原 `SaveError` 设置和脱敏流程，仅保存已有截图队列与日志，不为取现场再截图，不触发 LLM 分析、错误上传或清理旧现场。

预热、长等待后的首次主动启动仍允许；如果启动失败，后续兜底也记录待恢复状态并检查最新总开关，不能借主动任务绕过故障恢复授权。SSH 等旧平台的启停接口可能不返回布尔值，保留其调用顺序，但日志或手动管理结果会明确“未提供完成确认”，设备是否上线仍须后续连接检查，不能当作已完成业务任务。

## 三个 Issue 的独立结论

- [#1287](https://github.com/wess09/AzurPilot/issues/1287) 成立：旧代码关闭上限只清计数，选任务仍强制写回旧冷却。接受“只解除本进程拥有的故障排期”的建议，不重启或重新启用用户禁用的任务。
- [#1288](https://github.com/wess09/AzurPilot/issues/1288) 成立：旧超时检查漏总开关；监护和日报仅初始化创建。接受实时快照、按需创建/重建的建议，保留独立定时重启语义，不从后台加载和绑定任务。
- [#1289](https://github.com/wess09/AzurPilot/issues/1289) 成立：旧模拟器恢复入口明确忽略离线开关，阈值名称也把次数写成秒。按来源修复；不把离线开关误用成所有主动重启的总开关。Issue 没有要求增加全局恢复上限，此前添加该上限没有依据，已撤回。

## 自审与验证边界

| 用户要求的审查项 | 本次采取的检查 |
| --- | --- |
| 需求是否完整 | 检查任务异常、全局初始化/收尾异常、后端重试、局部客户端恢复、监护、调度入口、手动与定时来源 |
| 是否有无关修改 | 先完整撤回旧提交，以可运行基线逐文件审核；不改默认值、模拟器命令、启动超时阶梯或无关业务机制 |
| 兼容性 | 保留旧版脚本错误三次退出、SP 次日排期、一次未知页面原地恢复、客户端启动/观察、系统 Restart 豁免；原生构造的新配置参数可选 |
| 潜在 Bug | 检查平台失败返回值不伪装成功、卡死不冒充离线、未知异常不强制重启模拟器 |
| 并发/缓存/同步 | 检查后台只读快照、服务启用锁、平台互斥、阻塞游戏启停不叠加、原生对象配置传递、计划中断标记及冷却事务 |
| 安全与隐私 | 退出只作用于当前 worker；故障现场沿用脱敏和用户保存设置，不新增外部传输 |
| 测试缺口 | 使用真实工厂生成的原生对象（DLL 打桩）、真实隔离子进程退出、临时配置、真实调度循环和后台线程；真实模拟器验收尚未执行 |
| 是否更简单 | 保留原异常分支、平台启停和本地业务处理，只在恢复边界统一检查；删除此前外层预算和首次未知错误即停机的行为 |
| 命名与边界 | 离线、卡死、计划来源分开；游戏启动次数、错误检测次数、实际启停失败次数与业务恢复上限各司其职 |

针对性测试见 `test_recovery_authorization.py`、`test_scheduler_recovery.py`、`test_scheduler_live_loop.py`、`test_device_backend_retry.py`、`test_device_recovery.py`、`test_emulator_restart_mutex.py`；日报及战役续接等关联测试用于验证保留行为。

2026-10-23 最终 15 个相关测试模块合并执行，322 项通过；基础 Ruff、新增核心导入/未定义名称检查及差异空白检查通过。前端类型检查已尝试，但环境缺少 `tsc`，未完成；没有修改前端源码。日报同文件时间热启用、Restart 后撤销故障任务恢复等缺陷均保留了先失败、修复后通过的回归用例。

离线测试不能证明某台模拟器已经实际启动、游戏已经登录或真实 DLL 已恢复。仍需用户在指定实例上验收；无需改已有配置或安装新依赖。保留的深度重启配置仍可能影响同一 MuMu 安装的其他模拟器，这是原有能力，本次没有扩大它的作用范围。
